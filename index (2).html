Section 01

C'est quoi
la CI/CD ?

"Avant de toucher un outil, comprends pourquoi il existe."

Le problème sans CI/CD

Imagine une équipe de 5 développeurs qui travaillent sur le même projet. Chacun code de son côté, et le vendredi soir tout le monde pousse son code en même temps. Résultat : conflits, bugs, site cassé, soirée gâchée.

La CI/CD c'est ce qui évite ça.

CI

Intégration Continue

Chaque fois que tu pousses du code, des vérifications se déclenchent automatiquement — tests, analyse, compilation. L'objectif : détecter les erreurs avant qu'elles arrivent en production.

CD

Déploiement Continu

Une fois le code vérifié, il est automatiquement envoyé sur le serveur. Plus besoin de déployer à la main — c'est fiable, reproductible, et rapide.

L'analogie pour comprendre

Analogie
Pense à une chaîne de montage automobile. Chaque voiture passe par des contrôles qualité automatiques avant de quitter l'usine. Si un défaut est détecté, la chaîne s'arrête et alerte un technicien. Personne ne laisse partir une voiture défectueuse. Ton code, c'est pareil.
Sans CI/CD Avec CI/CD
Tests manuels Tests automatiques
Déploiement à la main Déploiement automatique
Erreurs découvertes tard Erreurs détectées immédiatement
Processus différent à chaque fois Processus identique et fiable

Section 02

Les notions clés
d'un pipeline

"Un pipeline c'est une chaîne d'étapes. Voici les pièces qui la composent."

pipeline

Pipeline

L'ensemble du processus automatisé — du git push jusqu'au déploiement final. La "chaîne" complète contenant plusieurs étapes dans un ordre précis.

stage

Stage (étape)

Un pipeline est découpé en grandes phases : Build, Test, Deploy. Chaque stage ne démarre que si le précédent a réussi.

runner

Runner

La machine virtuelle qui exécute ton pipeline. GitHub met à disposition ses propres runners — tu n'as rien à installer.

artifact

Artifact

Un fichier produit par le pipeline et conservé pour être réutilisé dans une étape suivante. Ex : résultat d'une compilation.

Section 03

GitHub Actions,
l'outil qui fait tout ça

"GitHub Actions c'est exactement ce qu'on vient de décrire, intégré directement dans ton repo."

GitHub Actions c'est l'outil de CI/CD intégré directement dans GitHub. Pas besoin d'un service externe, pas besoin de configurer un serveur séparé — tout se passe dans ton repo, dans un fichier YAML que tu crées toi-même.

C'est gratuit pour les repos publics, et largement suffisant pour des projets perso ou d'école.

Les 4 concepts clés

workflow

Workflow

Le fichier YAML entier. C'est ton pipeline complet, stocké dans .github/workflows/

event

Event

Ce qui déclenche le pipeline. push, pull_request, schedule... C'est le trigger qu'on a vu à la section précédente.

job

Job

Un groupe de tâches qui s'exécutent sur une même machine virtuelle (runner).

step

Step

Une action précise à l'intérieur d'un job — installer les dépendances, lancer les tests, déployer...

Schéma d'un workflow

workflow structure
git push
  ↓ Event déclenché
Workflow
  ↓
  Job 1 : Tests (ubuntu-latest)
    Step 1 : Installer les dépendances
    Step 2 : Lancer les tests
    Step 3 : Rapport de résultats
  ↓ (si tests OK)
  Job 2 : Déploiement
    Step 1 : Connexion au serveur
    Step 2 : Mise en ligne du code

Section 04

Anatomie d'un
fichier YAML

"GitHub Actions se configure avec un seul fichier. Voici comment le lire et l'écrire."

YAML c'est un langage de configuration — pas un langage de programmation. Tu ne codes pas, tu décris. Tu dis à GitHub Actions quoi faire, quand le faire, et dans quel ordre.

Règle absolue
L'indentation c'est tout. Une mauvaise indentation = pipeline cassé. On utilise des espaces, jamais des tabulations.

La structure de base annotée

■ .github/workflows/mon-pipeline.yml
name: Mon premier pipeline  # Nom visible sur GitHub
 
on:  # Trigger — quand se déclenche-t-il ?
  push:
    branches:
      - main  # Uniquement sur la branche main
 
jobs:  # Les tâches à exécuter
  mon-job:  # Nom du job
    runs-on: ubuntu-latest  # Machine virtuelle
 
    steps:  # Les étapes du job
      - name: Récupérer le code
        uses: actions/checkout@v3  # Action officielle
 
      - name: Dire bonjour
        run: echo "Pipeline lancé !"  # Commande shell

uses vs run — la différence

runuses
C'est quoiUne commande shellUne action préfabriquée
Exemplerun: npm testuses: actions/checkout@v3
Quand l'utiliserCommandes simplesTâches complexes réutilisables
Variables sensibles
Ne jamais écrire un mot de passe ou une clé API dans le fichier YAML. Utilise les Secrets GitHub (Settings → Secrets → Actions) et réfère-y avec ${{ secrets.MA_CLE }}
→ Tu connais maintenant les pièces du puzzle. On assemble tout ça.
Section 05

Ton premier pipeline
pas à pas

"On prend tout ce qu'on vient d'apprendre et on crée un vrai pipeline, de zéro."

Ce qu'on va construire

Un pipeline simple mais complet qui fait 2 choses à chaque git push sur la branche main : vérifie que le code ne contient pas d'erreurs, et affiche un message de confirmation si tout est OK.

01

Préparer ton repo

Dans ton repo GitHub, crée cette structure de dossiers :

structure du projet
ton-repo/
└── .github/
    └── workflows/
        └── premier-pipeline.yml
Pourquoi ce dossier ?
Le dossier .github/workflows/ c'est l'endroit que GitHub surveille automatiquement. Tout fichier .yml dedans sera interprété comme un workflow.
02

Écrire le fichier YAML

Copie ce fichier dans premier-pipeline.yml :

■ premier-pipeline.yml
name: Mon Premier Pipeline CI
 
on:
  push:
    branches:
      - main
 
jobs:
  verification:
    runs-on: ubuntu-latest
 
    steps:
      - name: Récupérer le code
        uses: actions/checkout@v3
 
      - name: Afficher la structure du projet
        run: ls -la
 
      - name: Pipeline réussi
        run: echo "Tout s'est bien passé !"
03

Pousser le code

bash
$ git add .
$ git commit -m "feat: ajout du premier pipeline CI"
$ git push origin main
✓ Enumerating objects: 5, done.
✓ Writing objects: 100% (3/3), done.
